## Root cause and design

The previous implementation rejected all explicit container UUIDs in the leaf
normalizer, while recursive emptying intentionally returned a verified no-op
when a container had no descendants. This was a public contract limitation, not
a QLab, UUID, token, or readback failure.

The minimal boundary is now:

| Request | Result |
| --- | --- |
| `cue_ids` with a leaf UUID | Existing leaf Delete behavior |
| `container_id`, `recursive=false` | Delete exactly one inactive empty `Group` |
| `container_id`, `recursive=true` | Existing deepest-first descendant Delete; root preserved |
| Direct Cue List, Cue Cart, or Cart | Rejected; recursive-only |
| Direct non-empty Group | Rejected; use reviewed recursive mode |

The direct Group is represented as a one-item plan. The existing
`confirm:deleteCues:v1` token binds the exact UUID, QLab type, parent, sibling
order, child list (empty), health/activity/readiness snapshots, tree
fingerprint, and deletion-impact fingerprint. Real execution remains one
sequential mutator followed by fresh absence and neighbor readback; no retry or
automatic rollback was added.

3. Review of the one-item plan and fresh `confirm:deleteCues:v1` token.
